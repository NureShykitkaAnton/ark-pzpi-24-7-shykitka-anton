2 РОЗРОБКА БАЗИ ДАНИХ ТА ПРИКЛАДНОГО ПРОГРАМНОГО ІНТЕРФЕЙСУ СЕРВЕРНОЇ ЧАСТИНИ
2.1 Розробка будови програмної системи та опис інженерних рішень
Відповідно до концепції та рамок проєкту (Vision & Scope), «Програмна система для контролю енергоспоживання будинку» (власна назва EnergyMonitor) складається з чотирьох взаємопов'язаних компонентів: мікроконтролерного IoT-клієнта на платформі ESP32, центральної серверної частини з реляційною базою даних, браузерного вебклієнта на базі React 19 та кросплатформового мобільного застосунку на платформі Capacitor 8. Центральною ланкою системи є серверна частина, яка приймає потік телеметрії, забезпечує збереження часових рядів, виконує тарифні й бюджетні розрахунки, детектує аномалії навантаження, формує запити до великих мовних моделей (LLM) та надає засоби системного адміністрування.
Серверну частину реалізовано мовою програмування Python 3.14 із використанням асинхронного програмного каркаса FastAPI, високопродуктивного асинхронного драйвера asyncpg, реляційної системи управління базами даних PostgreSQL 18 та системи керування міграціями схеми даних Alembic. Інфраструктурне середовище розгортається у контейнерах Docker за допомогою Docker Compose із маршрутизацією захищеного HTTPS-трафіку через зворотний проксі-сервер Traefik v3.
В основу будови серверного застосунку покладено модульну архітектуру вертикальних зрізів (Vertical Slice Architecture), яка забезпечує низьку зв'язність та високу згуртованість програмних компонентів. Програмний код розділено на два рівні:
1) Базове ядро (пакет app/core) – містить спільні інфраструктурні компоненти: модуль налаштувань середовища (config.py), ініціалізацію асинхронного рушія та генератора транзакційних сесій бази даних (database.py), декларативну базу моделей і міксини ідентифікаторів та часових міток (models.py), узагальнений шаблонний репозиторій (repositories.py), ієрархію прикладних винятків (exceptions.py) та криптографічний модуль безпеки (security.py);
2) Рівень бізнес-доменів (пакет app/modules) – містить десять ізольованих предметних модулів: health (діагностика стану сервера та з'єднання з СУБД), auth (реєстрація, автентифікація та ротація сесійних токенів), users (профілі користувачів, ролі, підписки та параметри локалізації), tariffs (однозонні й двозонні тарифні плани «день/ніч»), lines (лінії живлення та реєстрація давачів ESP32), budgets (місячні фінансові ліміти та прогнозування витрат), telemetry (прийом пакетів вимірювань, контроль часових пропусків та збереження профілів навантаження), anomalies (фіксація стрибків потужності, маркування приладів та LLM-пояснення), notifications (реєстрація токенів FCM/APNs та журнал сповіщень) і admin (журнал аудиту, резервне копіювання бази даних, перевірка цілісності відновлення, експорт та імпорт конфігурацій). Кожен модуль структуровано за єдиним стандартом: models.py, schemas.py, repository.py, service.py, dependencies.py та router.py.
Прийнято такі ключові інженерні рішення щодо безпеки, інтернаціоналізації та захисту персональних даних (відповідно до GDPR): паролі користувачів хешуються криптостійким алгоритмом Argon2id; авторизація клієнтських запитів здійснюється за допомогою короткоживучих JWT access-токенів та довгоживучих refresh-токенів із обов'язковою ротацією та збереженням SHA-256 хешу у базі даних; автентифікація апаратних модулів ESP32 виконується за окремим заголовком X-Device-Token (у базі даних зберігається лише його SHA-256 дайджест); усі часові мітки зберігаються у форматі TIMESTAMPTZ в універсальному часі UTC із підтримкою української (uk) та англійської (en) локалей, часових поясів користувачів і систем одиниць вимірювання; при видаленні облікового запису виконується м'яке видалення з повною анонімізацією персональних даних.
2.2 Розробка UML-діаграми прецедентів для серверної частини системи
Для формалізації функціональних вимог до серверної частини системи (розділ 2.3.1 документа Vision & Scope) розроблено UML-діаграму прецедентів, яка відображає взаємодію п'яти зовнішніх акторів із дев'ятнадцятьма прецедентами використання серверної частини:
– Побутовий споживач / корпоративний користувач (B2B) – реєструється та проходить автентифікацію (UC-1), налаштовує параметри локалізації й часового поясу (UC-2), створює тарифні сітки «день/ніч» (UC-3), реєструє лінії живлення (UC-4, що обов'язково включає прецедент генерації API-токена для ESP32 — UC-5 за відношенням «include»), встановлює місячні бюджети (UC-6), переглядає часові ряди телеметрії й агреговану статистику (UC-7), зберігає та повторно програє профілі навантаження за альтернативними тарифами (UC-8), переглядає аномальні стрибки потужності й позначає увімкнені побутові прилади (UC-9, який за відношенням «extend» може розширюватися прецедентом генерації текстового пояснення від LLM, UC-10), управляє токенами сповіщень (UC-11) та експортує або імпортує власні конфігурації (UC-16);
– Адміністратор системи – успадковує всі можливості споживача та додатково виконує керування обліковими записами й рівнями підписки Free/Pro (UC-17), переглядає журнал аудиту дій (UC-18), створює резервні копії бази даних і перевіряє цілісність їх відновлення (UC-19);
– IoT-клієнт (мікроконтролер ESP32) – передає на сервер пакети вимірювань у реальному часі або накопичені пачки відліків із кільцевого буфера оперативної пам'яті після відновлення зв'язку (UC-12), що автоматично включає («include») контроль часових пропусків та лінійну інтерполяцію (UC-13), детектування стрибків потужності ΔP та перевантажень за струмом (UC-14), а також перерахунок бюджету й перевірку порогів 80% та 100% (UC-15);
– Зовнішній сервіс LLM та сервіси push-сповіщень (FCM / APNs) – залучаються серверною частиною під час виконання прецедентів формування інтелектуальних пояснень динаміки витрат (UC-10) та доставлення миттєвих попереджень на смартфони користувачів (UC-11).

2.3 Розробка ER-діаграми даних
На основі визначених прецедентів використання побудовано концептуальну модель даних «Сутність – Зв'язок» (ER-діаграму) у нотації «вороняча лапка» (Crow's Foot). Схема даних охоплює 12 взаємопов'язаних сутностей, нормалізованих до третьої нормальної форми (3НФ), що усуває надлишкове дублювання атрибутів і забезпечує цілісність даних при транзакційних операціях.
Центральними стрижневими сутностями моделі є USERS (користувачі) та POWER_LINES (лінії живлення). Один запис сутності USERS перебуває у відношенні «один-до-багатьох» (1:N) із сутностями REFRESH_TOKENS (сесійні токени), TARIFFS (налаштовані тарифні плани), POWER_LINES (зареєстровані лінії обліку), PUSH_TOKENS (мобільні пристрої користувача), NOTIFICATIONS (історія сповіщень), AUDIT_LOGS (записи журналу аудиту) та SYSTEM_BACKUPS (створені резервні копії). Сутність TARIFFS пов'язана відношенням 1:N із сутністю POWER_LINES, визначаючи правила тарифікації для конкретної лінії. Своєю чергою, кожна лінія живлення (POWER_LINES) має відношення 1:N із місячними бюджетами (BUDGETS), часовими рядами телеметрії (TELEMETRY_READINGS), зафіксованими аномаліями (ANOMALY_EVENTS), збереженими профілями навантаження (LOAD_PROFILES) та сповіщеннями (NOTIFICATIONS). 2.4 Розробка бази даних та діаграми структури бази даних
Фізичну схему бази даних реалізовано для реляційної СУБД PostgreSQL 18. Як первинний ключ (PK) в усіх дванадцяти таблицях використано 128-бітний тип UUID із генерацією значень за стандартом UUIDv7. На відміну від випадкового UUIDv4, стандарт UUIDv7 містить часову складову у старших бітах, завдяки чому нові записи (зокрема інтенсивний потік у таблиці telemetry_readings) вставляються послідовно в кінець B-Tree індексу без його фрагментації. Для всіх грошових та фізичних величин використано точний тип фіксованої розрядності NUMERIC(p, s), що унеможливлює похибки округлення чисел із рухомою комою під час фінансових розрахунків. Призначення кожної таблиці бази даних систематизовано в таблиці 2.1.

load_profiles | Архів еталонних та історичних профілів навантаження у форматі JSONB для ретроспективного аналізу й моделювання витрат під час повторного програвання.

Для забезпечення цілісності даних на рівні СУБД накладено перевірочні обмеження CHECK (додатність тарифних ставок, номінальної напруги, граничного струму, суми бюджетного ліміту; допустимі межі нічного коефіцієнта від 0 до 1; номер місяця від 1 до 12) та унікальні обмеження UNIQUE (унікальність електронної пошти, апаратного ідентифікатора device_uid, хешів токенів та комбінації лінії, року й місяця у таблиці budgets). 2.5 Розробка функцій роботи з базою даних (ORM та репозиторії)
Взаємодію серверної частини з базою даних реалізовано за допомогою асинхронного об'єктно-реляційного відображення (ORM) SQLAlchemy 2 із використанням шаблону проєктування «Репозиторій» (Repository). У модулі app/core/models.py оголошено декларативний базовий клас Base та спільні міксини UUIDMixin і TimestampMixin, а в модулі app/core/repositories.py реалізовано узагальнений параметризований клас BaseRepository[ModelType], який інкапсулює типові асинхронні операції читання за первинним ключем (get_by_id), вибірки списку з пагінацією (get_all), створення (create), часткового оновлення (update) та видалення (delete) записів у межах транзакційної сесії AsyncSession.
Фрагмент програмного коду узагальненого базового репозиторію наведено в лістингу 2.1, а повний код моделей, управління сесіями та спеціалізованих репозиторіїв предметних модулів винесено в Додаток А (лістинги А.1–А.5).

2.7 Програмна реалізація та перевірка роботи серверної частини системи
Для перевірки працездатності створеної бази даних та прикладного програмного інтерфейсу розгорнуто контейнери СУБД PostgreSQL 18 (energymon-db) і вебінтерфейсу адміністрування бази даних pgweb (energymon-pgweb) за допомогою Docker Compose. Виконано застосування початкової міграції схеми даних командою uv run alembic upgrade head (ревізія 0001_initial_schema), у результаті чого в базі даних energymon створено всі 12 таблиць, обмеження цілісності та індекси.
Перевірку взаємодії серверної частини з базою даних та клієнтами виконано за допомогою автоматизованого інтеграційного тестового набору tests/test_energy_monitor_api.py на базі pytest та асинхронного клієнта httpx.AsyncClient (повний код наведено в Додатку В, лістинг В.1). Наскрізний тест послідовно перевіряє такі етапи:
1) перевірку стану з'єднання з базою даних через GET /api/v1/health (отримано статус 200 OK, database: connected);
2) реєстрацію нового користувача через POST /api/v1/auth/register із хешуванням пароля Argon2id та видачею JWT-токенів;
3) створення двозонного тарифу «День/Ніч» (ставка 4,32 грн/кВт·год, нічний коефіцієнт 0,5 з 23:00 до 07:00) через POST /api/v1/tariffs;
4) реєстрацію лінії живлення та давача ESP32 через POST /api/v1/lines із генерацією секретного ключа X-Device-Token та встановлення місячного фінансового бюджету через POST /api/v1/budgets;
5) пакетне завантаження відліків телеметрії від імені пристрою ESP32 через POST /api/v1/telemetry/ingest, під час якого сервер автоматично виявив часовий розрив у 25 с, створив інтерпольований відлік (is_interpolated = true), зафіксував стрибок активної потужності ΔP > 800 Вт у таблиці anomaly_events та оновив накопичені витрати й прогноз у таблиці budgets;
6) отримання агрегованої статистики споживання (GET /api/v1/telemetry/summary), позначення приладу користувачем (PATCH /api/v1/anomalies/{id}/label), генерацію пояснення від LLM (POST /api/v1/anomalies/{id}/explain), збереження й повторне програвання профілю навантаження (POST /api/v1/telemetry/profiles/{id}/replay), реєстрацію мобільного токена сповіщень (POST /api/v1/notifications/push-tokens) та експорт конфігурації з контрольною сумою SHA-256 (GET /api/v1/admin/export).
Усі інтеграційні тести (test_health_check та test_full_energy_monitor_workflow) виконано успішно. Додатково програмний код перевірено засобами статичного аналізу ruff check та перевірки типів ty check app — порушень стандартів оформлення або помилок типізації не виявлено.

 11 
 12 class BaseRepository[ModelType: Base]:
 13     """Базовий клас репозиторію за шаблоном проектування Repository."""
 14 
 15     def __init__(self, model: type[ModelType], session: AsyncSession) -> None:
 16         self.model = model
 17         self.session = session
 18 
 19     async def get_by_id(self, id: Any) -> ModelType | None:
 20         """Повертає запис за первинним ключем або None, якщо запис відсутній."""
 21         return await self.session.get(self.model, id)
 22 
 23     async def get_all(self, skip: int = 0, limit: int = 100) -> Sequence[ModelType]:
 24         """Повертає список записів із підтримкою пагінації (skip, limit)."""
 25         query = select(self.model).offset(skip).limit(limit)
 26         result = await self.session.execute(query)
 27         return result.scalars().all()
 28 
 29     async def create(self, **kwargs: Any) -> ModelType:
 30         """Створює новий екземпляр моделі у поточній сесії БД та оновлює його стан."""
 31         instance = self.model(**kwargs)
 32         self.session.add(instance)
 33         await self.session.flush()
 34         await self.session.refresh(instance)
 35         return instance
 36 
 37     async def update(
 38         self, db_obj: ModelType, *, exclude_none: bool = True, **kwargs: Any
 39     ) -> ModelType:
 40         """Частково або повністю оновлює поля існуючого об'єкта моделі."""
 41         for key, value in kwargs.items():
 42             if hasattr(db_obj, key) and not (exclude_none and value is None):
 43                 setattr(db_obj, key, value)
 44         self.session.add(db_obj)
 45         await self.session.flush()
 46         await self.session.refresh(db_obj)
 47         return db_obj
 48 
 49     async def delete(self, db_obj: ModelType) -> None:
 50         """Фізично видаляє переданий об'єкт із бази даних."""
 51         await self.session.delete(db_obj)
 52         await self.session.flush()
