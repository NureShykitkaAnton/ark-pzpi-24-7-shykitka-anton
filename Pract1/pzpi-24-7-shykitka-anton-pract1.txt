2 ЗАВДАННЯ
Мета роботи: ознайомитися з основними рекомендаціями та промисловими стандартами щодо написання чистого, ефективного, читабельного та підтримуваного програмного коду у мові програмування PHP, а також набути практичних навичок аналізу, форматування, документування та автоматизованої перевірки якості коду.
Постановка завдання згідно з методичними вказівками до практичного заняття № 1 на тему «Правила оформлення програмного коду»:
1. Обрати мову програмування для поглибленого аналізу правил оформлення програмного коду (обрано мову програмування PHP).
2. Дослідити основні стандарти та рекомендації для написання якісного коду у мові PHP, зокрема стандарти групи PHP-FIG (PSR-1, PSR-4, PSR-12, PER Coding Style 2.0): структуру проєкту та файлів, форматування коду, конвенції іменування, правила коментування та документування (PHPDoc), підходи до розробки через тестування (TDD) та інструменти автоматизації статичного аналізу.
3. Підготувати наочні практичні приклади програмного коду мовою PHP («поганий» та «гарний» приклади до та після застосування правил оформлення), обґрунтувати кожну рекомендацію та надати розгорнуті пояснення.
4. Створити презентацію з 12 слайдів українською мовою, записати відеодоповідь тривалістю 7–9 хвилин та оформити звіт відповідно до вимог стандарту ДСТУ 3008:2015.

3 ОПИС ВИКОНАНОЇ РОБОТИ
3.1 Важливість правил оформлення коду та стандарти PHP-FIG
Програмний код у сучасних комерційних та відкритих проєктах читається розробниками значно частіше, ніж пишеться. Як зазначає Роберт Мартін у праці «Clean Code», співвідношення часу, витраченого на читання наявного коду, до часу написання нового коду перевищує 10 до 1. Відсутність єдиних правил оформлення призводить до того, що кодова база перетворюється на неоднорідну суміш індивідуальних стилів, що суттєво ускладнює її розуміння, підвищує ризик внесення дефектів та уповільнює процес взаємного перегляду коду (Code Review).
Історично мова програмування PHP розвивалася без єдиного вбудованого стандарту форматування, тому різні фреймворки (Symfony, Laravel, Zend/Laminas, Yii) використовували власні конвенції. Для вирішення цієї проблеми у 2009 році була створена робоча група PHP-FIG (PHP Framework Interop Group), яка розробила серію стандартів PSR (PHP Standards Recommendations). Станом на сьогодні ключовими стандартами оформлення коду в екосистемі PHP є:
– PSR-1 (Basic Coding Standard) — базовий стандарт кодування, що визначає фундаментальні вимоги до сумісності спільного PHP-коду (теги, кодування файлів, правила іменування класів, констант та методів);
– PSR-4 (Autoloader) — стандарт автоматичного завантаження класів на основі просторів імен та ієрархії каталогів проєкту;
– PSR-12 (Extended Coding Style) — розширений посібник зі стилю кодування, який замінив застарілий стандарт PSR-2 та деталізував правила відступів, довжини рядків, розташування дужок і типізації;
– PER Coding Style 2.0 (PHP Evolving Recommendations) — еволюційне продовження PSR-12, що враховує нові синтаксичні конструкції сучасного PHP 8.x (перелічувані типи Enum, атрибути, readonly-класи, просування властивостей у конструкторі та типи перетину).
3.2 Структура проєкту та організація файлів
Правильна архітектурна організація PHP-проєкту базується на стандарті автозавантаження PSR-4 та принципі розділення відповідальності. Типова структура сучасного PHP-застосунку передбачає чіткий розподіл файлів за такими каталогами: директорія src/ містить вихідний код бізнес-логіки та доменних моделей (відповідає кореневому простору імен App\); директорія tests/ містить модульні та інтеграційні тести (простір імен Tests\); директорія public/ містить єдину публічну точку входу вебзастосунку (index.php) та статичні ресурси; директорія config/ зберігає конфігураційні файли; директорія vendor/ містить зовнішні залежності, встановлені через пакетний менеджер Composer.
Кожен файл вихідного коду повинен відповідати правилу «один клас — один файл»: в одному файлі оголошується рівно один клас, інтерфейс, трейт або перелік (enum), а назва файлу повинна точно збігатися з назвою цього класу з урахуванням регістру символів (наприклад, клас OrderServiceClean розміщується у файлі src/Service/OrderServiceClean.php). Згідно з PSR-1, файл повинен або оголошувати нові символи (класи, функції, константи), або виконувати побічні ефекти (виведення даних, зміна налаштувань ini, підключення файлів), але категорично заборонено поєднувати обидві дії в одному файлі.
Заголовок кожного PHP-файлу за стандартом PSR-12 має чітко визначений порядок блоків, розділених одним порожнім рядком: відкриваючий тег <?php; директива суворої типізації declare(strict_types=1);; оголошення простору імен namespace; згруповані та відсортовані за алфавітом інструкції імпорту use; блок документації та оголошення самого класу.
3.3 Форматування коду, відступи та стандарти для дужок
Стандарт PSR-12 встановлює однозначні правила форматування вихідного тексту програм мовою PHP:
1. Кодування та теги: усі PHP-файли мають зберігатися у кодуванні UTF-8 без маркера BOM (Byte Order Mark) і використовувати виключно символ переведення рядка LF (\n). Дозволяється використовувати лише повний тег <?php або короткий ехо-тег <?=; у файлах, що містять виключно PHP-код, закриваючий тег ?> опускається, щоб запобігти випадковому відправленню пробільних символів у буфер HTTP-відповіді.
2. Відступи та довжина рядків: для формування відступів використовується рівно 4 пробіли; використання символів табуляції (\t) заборонено, оскільки вони по-різному відображаються у різних редакторах та системах перегляду коду. Рекомендована (м’яка) межа довжини рядка становить 80 символів, а жорсткий ліміт — 120 символів. В одному рядку не повинно бути більше однієї інструкції.
3. Стилі розташування фігурних дужок (Allman та K&R): характерною особливістю стандарту PSR-12 у PHP є комбіноване використання двох класичних стилів. Для оголошення класів, інтерфейсів, трейтів і методів застосовується стиль Allman — відкриваюча фігурна дужка { переноситься на окремий рядок під заголовком оголошення на тому самому рівні відступу. Натомість для керуючих конструкцій (if, elseif, else, foreach, for, while, do, switch, try, catch) застосовується стиль K&R (One True Brace Style) — відкриваюча фігурна дужка { ставиться у тому самому рядку через один пробіл після закриваючої круглої дужки умови. Якщо список параметрів методу розбивається на декілька рядків (багаторядкова сигнатура), закриваюча кругла дужка, двокрапка з типом повернення та відкриваюча фігурна дужка тіла методу розміщуються разом на одному рядку: ): float {.
3.4 Іменування змінних, функцій, класів та констант
Дотримання конвенцій іменування робить програмний код самодокументованим та усуває потребу в зайвих пояснювальних коментарях. У мові PHP за стандартами PSR-1 та PSR-12 діють такі правила:
– Класи, інтерфейси, трейти та переліки (Enum) іменуються у стилі PascalCase (StudlyCaps) і мають бути іменниками у однині, що чітко відображають сутність або її роль у системі (наприклад, OrderProcessorClean, DiscountPolicyInterface, PaymentGateway).
– Методи та функції іменуються виключно у стилі camelCase і повинні починатися з дієслова, яке описує виконувану дію (наприклад, calculateTotal(), resolveDiscountRate(), validateItems()). Для методів і змінних, що повертають або зберігають логічне значення (bool), рекомендується використовувати префікси is, has, can, should (наприклад, $isExpressDelivery, isActive(), hasPermission()).
– Змінні та властивості класів іменуються у стилі camelCase ($customerType, $discountAmount, $taxableSubtotal). Слід уникати однобуквених імен ($s, $u, $f) та незрозумілих скорочень ($ord_proc, $arr), за винятком лічильників у коротких математичних циклах.
– Константи класів і глобальні константи іменуються у стилі UPPER_SNAKE_CASE великими літерами з розділенням слів символом підкреслення (наприклад, DEFAULT_TAX_RATE, EXPRESS_DELIVERY_FEE, CUSTOMER_VIP). Усі «магічні числа» (числові літерали з неочевидним змістом, такі як 0.15, 1.2, 1000) обов’язково виносяться в іменовані типізовані константи з модифікатором видимості (наприклад, private const float VAT_MULTIPLIER = 1.20;).
3.5 Коментарі та документування коду (PHPDoc)
Якісний програмний код повинен мінімізувати потребу у звичайних коментарях за рахунок виразного іменування та декомпозиції великих функцій на малі приватні методи. Однорядкові коментарі (//) доречні лише тоді, коли потрібно пояснити причину («чому») вибору певного алгоритму, бізнес-обмеження або обхідного рішення, а не дублювати те, «що» вже видно з синтаксису мови. Залишати у коді закоментовані фрагменти старих реалізацій суворо заборонено — історію змін відстежує система контролю версій Git.
Для формалізованого документування програмних інтерфейсів у PHP використовується стандарт PHPDoc (блоки /** ... */). У сучасних версіях PHP 8.x більшість скалярних і об’єктних типів вказуються нативно у сигнатурі методу (int, float, string, bool, array), тому не потрібно дублювати у PHPDoc очевидні теги, якщо вони не додають нової інформації. Водночас блоки PHPDoc є незамінними для:
– опису призначення класу чи методу та особливостей бізнес-логіки;
– деталізації структури масивів та узагальнених колекцій за допомогою анотацій для статичних аналізаторів, наприклад: @param array<int, array{price: float, quantity: int}> $items;
– документування винятків, які може згенерувати метод, за допомогою тегу @throws InvalidArgumentException.
3.6 Інструменти статичного аналізу, автоматизації та TDD у PHP
Ручна перевірка дотримання правил оформлення коду є неефективною, тому у промисловій розробці на PHP контроль якості повністю автоматизується за допомогою спеціалізованих інструментів:
1. Лінтери та форматери стилю: пакет PHP_CodeSniffer (складається з утиліти перевірки phpcs та утиліти автовиправлення phpcbf) перевіряє відповідність коду стандарту PSR-12. Інструменти PHP-CS-Fixer та Laravel Pint дозволяють автоматично форматувати код відповідно до правил PSR-12 та PER Coding Style 2.0.
2. Статичні аналізатори коду: інструменти PHPStan та Psalm виконують глибокий аналіз потоків виконання та типів даних без фактичного запуску програми (за шкалою суворості від рівня 0 до рівня 9). Комплексні платформи SonarQube та Codacy відстежують «запахи коду» (code smells), цикломатичну складність методів, потенційні вразливості безпеки та відсоток дублювання коду.
3. Автоматизація перевірок: локально перед кожним комітом використовуються Git Hooks (наприклад, через пакети CaptainHook або Husky), які запускають phpcs та phpstan для змінених файлів. На рівні репозиторію налаштовується конвеєр безперервної інтеграції CI/CD (GitHub Actions або GitLab CI), який автоматично блокує злиття Pull Request, якщо виявлено порушення код-стайлу або падіння тестів.
4. Кодування на основі тестування (Test-Driven Development, TDD): використання фреймворку PHPUnit за циклом Red — Green — Refactor спонукає розробника проєктувати слабко зв’язані класи з чіткими контрактами та ін’єкцією залежностей (Dependency Injection). Тестові методи оформлюються за шаблоном Arrange (підготовка даних) — Act (виклик тестованого методу) — Assert (перевірка результату), що робить тести наочною живою документацією системи.
3.7 Аналіз практичних прикладів оформлення коду
Для демонстрації розглянутих рекомендацій було розроблено та проаналізовано комплект прикладів програмного коду мовою PHP, наведений у Додатку В.
У підрозділі В.1 (файл OrderServiceClean.php) наведено еталонний приклад сервісного класу розрахунку вартості замовлення, який демонструє використання суворої типізації declare(strict_types=1), автозавантаження за PSR-4, модифікатора final, просування readonly-властивостей у конструкторі PHP 8.2+, типізованих констант у стилі UPPER_SNAKE_CASE та вичерпного документування PHPDoc із тегом @throws.
У підрозділі В.2 (файл OrderProcessorBad.php) наведено приклад неоформленого коду, який містить типові порушення стандартів: назву класу у snake_case (ord_proc), публічне поле з однобуквеним ім’ям ($d), відсутність модифікаторів видимості та декларацій типів у методі calc($u, $arr, $f), використання циклу for замість foreach, глибоку вкладеність умовних операторів, наявність шести «магічних чисел» (1, 2, 1000, 0.15, 0.05, 0.25, 150, 1.2), надлишкові коментарі та зайвий закриваючий тег ?>.
У підрозділі В.3 (файл OrderProcessorClean.php) показано результат приведення цього коду до вимог стандартів PSR-1 та PSR-12. Клас перейменовано на OrderProcessorClean у просторі імен App\Billing, усі магічні числа винесено в змістовні приватні константи (CUSTOMER_VIP, BULK_ORDER_THRESHOLD, EXPRESS_DELIVERY_FEE, VAT_MULTIPLIER), а монолітний метод декомпозовано на три чисті типізовані методи: calculateTotal(), calculateSubtotal() та resolveDiscountRate(). У підрозділі В.4 (файл OrderProcessorTest.php) наведено модульний тест PHPUnit, який перевіряє правильність роботи відрефактореного класу за структурою Arrange-Act-Assert.

4 ВИСНОВКИ
У результаті виконання практичного завдання № 1 було досліджено правила та промислові стандарти оформлення програмного коду у мові програмування PHP. Основні підсумки роботи полягають у такому:
– Було розглянуто еволюцію та ключові вимоги стандартів робочої групи PHP-FIG: базового стандарту кодування PSR-1, стандарту автозавантаження класів PSR-4, розширеного стандарту стилю PSR-12 та сучасних рекомендацій PER Coding Style 2.0.
– Досліджено правила організації структури проєкту, оформлення заголовків файлів із директивою declare(strict_types=1), форматування відступів (4 пробіли), обмеження довжини рядків (80–120 символів) та комбінованого застосування стилів дужок Allman (для класів і методів) та K&R (для керуючих конструкцій).
– Проаналізовано конвенції іменування сутностей у PHP (PascalCase для класів, camelCase для методів і змінних, UPPER_SNAKE_CASE для констант), практики уникнення «магічних чисел» та правила документування коду за допомогою блоків PHPDoc у поєднанні з нативною системою типів PHP 8+.
– Отримано практичні навички рефакторингу та приведення неоформленого PHP-коду до стандартів PSR-1 та PSR-12, а також застосування інструментів автоматичної перевірки якості коду (PHP_CodeSniffer, PHP-CS-Fixer, PHPStan, SonarQube) та модульного тестування за методологією TDD (PHPUnit).

 1  <?php
 2  
 3  declare(strict_types=1);
 4  
 5  namespace App\Service;
 6  
 7  use App\Contract\DiscountPolicyInterface;
 8  use App\Model\Order;
 9  use InvalidArgumentException;
10  
11  /**
12   * Сервіс розрахунку вартості замовлення згідно зі стандартами PSR-1 та PSR-12.
13   */
14  final class OrderServiceClean
15  {
16      public const float DEFAULT_TAX_RATE = 0.20;
17      private const int MIN_ORDER_ITEMS = 1;
18  
19      public function __construct(
20          private readonly DiscountPolicyInterface $discountPolicy,
21          private readonly float $taxRate = self::DEFAULT_TAX_RATE,
22      ) {
23      }
24  
25      /**
26       * Обчислює підсумкову вартість замовлення з урахуванням знижки та податку.
27       *
28       * @param Order $order Об'єкт замовлення клієнта.
29       * @return float Підсумкова сума до сплати.
30       * @throws InvalidArgumentException Якщо замовлення не містить товарів.
31       */
32      public function calculateFinalTotal(Order $order): float
33      {
34          if ($order->getItemsCount() < self::MIN_ORDER_ITEMS) {
35              throw new InvalidArgumentException('Замовлення повинно містити щонайменше один товар.');
36          }
37  
38          $subtotal = $order->getSubtotal();
39          $discountAmount = $this->discountPolicy->calculateDiscount($order);
40          $taxableAmount = max(0.0, $subtotal - $discountAmount);
41  
42          return round($taxableAmount * (1 + $this->taxRate), 2);
43      }
44  }

В.3 Приклад програмного коду після приведення до стандартів PSR-1 та PSR-12
GitHub репозиторій: https://github.com/NureShykitkaAnton/ark-pzpi-24-7-shykitka-anton/blob/main/Pract1/examples/OrderProcessorClean.php
 1  <?php
 2  
 3  declare(strict_types=1);
 4  
 5  namespace App\Billing;
 6  
 7  use InvalidArgumentException;
 8  
 9  /**
10   * Клас для обробки та розрахунку вартості замовлень клієнтів.
11   */
12  final class OrderProcessorClean
13  {
14      private const int CUSTOMER_REGULAR = 1;
15      private const int CUSTOMER_VIP = 2;
16  
17      private const float BULK_ORDER_THRESHOLD = 1000.0;
18      private const float REGULAR_BULK_DISCOUNT = 0.15;
19      private const float REGULAR_BASE_DISCOUNT = 0.05;
20      private const float VIP_DISCOUNT = 0.25;
21      private const float EXPRESS_DELIVERY_FEE = 150.0;
22      private const float VAT_MULTIPLIER = 1.20;
23  
24      /**
25       * Розраховує фінальну суму замовлення з ПДВ та доставкою.
26       *
27       * @param int $customerType Тип клієнта (1 - звичайний, 2 - VIP).
28       * @param array<int, array{price: float, quantity: int}> $items Список позицій замовлення.
29       * @param bool $isExpressDelivery Чи обрано експрес-доставку.
30       * @return float Підсумкова сума до сплати.
31       */
32      public function calculateTotal(
33          int $customerType,
34          array $items,
35          bool $isExpressDelivery = false,
36      ): float {
37          $subtotal = $this->calculateSubtotal($items);
38          $discountRate = $this->resolveDiscountRate($customerType, $subtotal);
39          $discountedTotal = $subtotal * (1.0 - $discountRate);
40  
41          if ($isExpressDelivery) {
42              $discountedTotal += self::EXPRESS_DELIVERY_FEE;
43          }
44  
45          return round($discountedTotal * self::VAT_MULTIPLIER, 2);
46      }
47  
48      /**
49       * @param array<int, array{price: float, quantity: int}> $items
50       */
51      private function calculateSubtotal(array $items): float
52      {
53          $subtotal = 0.0;
54  
55          foreach ($items as $item) {
56              if ($item['quantity'] <= 0) {
57                  continue;
58              }
59  
60              if ($item['price'] < 0) {
61                  throw new InvalidArgumentException('Ціна товару не може бути від’ємною.');
62              }
63  
64              $subtotal += $item['price'] * $item['quantity'];
65          }
66  
67          return $subtotal;
68      }
69  
70      private function resolveDiscountRate(int $customerType, float $subtotal): float
71      {
72          if ($customerType === self::CUSTOMER_VIP) {
73              return self::VIP_DISCOUNT;
74          }
75  
76          if ($customerType !== self::CUSTOMER_REGULAR) {
77              return 0.0;
78          }
79  
80          return $subtotal > self::BULK_ORDER_THRESHOLD
81              ? self::REGULAR_BULK_DISCOUNT
82              : self::REGULAR_BASE_DISCOUNT;
83      }
84  }
