2 ЗАВДАННЯ
Мета роботи: навчитися основним методам рефакторингу програмного коду на основі реальних прикладів із власних програмних проєктів, опанувати техніки ідентифікації проблемних ділянок у коді («запахів коду») та практичного застосування каталогу рефакторингів Мартіна Фаулера для підвищення якості, читабельності й підтримуваності програмного забезпечення без зміни його зовнішньої функціональності.
Постановка завдання згідно з методичними вказівками до практичного заняття № 2 на тему «Методи рефакторингу коду програмного забезпечення»:
1. Обрати три методи рефакторингу коду з класичної праці Мартіна Фаулера «Refactoring. Improving the Design of Existing Code»: Encapsulate Field (Інкапсуляція поля), Replace Nested Conditional with Guard Clauses (Заміна вкладених умовних операторів захисними умовами) та Replace Magic Number with Symbolic Constant (Заміна магічного числа символьною константою).
2. Для кожного з трьох обраних методів рефакторингу навести приклади власного програмного коду до та після проведення рефакторингу.
3. Детально описати проблему, яку вирішує кожен метод, пояснити процес перетворення коду та обґрунтувати технічні й архітектурні переваги отриманого рішення.
4. Підготувати презентацію з 12 слайдів українською мовою, записати відеодоповідь тривалістю 7–9 хвилин та оформити звіт відповідно до вимог стандарту ДСТУ 3008:2015.

3 ОПИС ВИКОНАНОЇ РОБОТИ
3.1 Теоретичні засади та призначення рефакторингу коду
Згідно з класичним визначенням Мартіна Фаулера, рефакторинг (refactoring) — це контрольований процес зміни внутрішньої структури програмного забезпечення без зміни його зовнішньої спостережуваної поведінки, метою якого є спрощення розуміння коду та зниження витрат на його подальшу модифікацію. У процесі активної розробки та додавання нових функцій під тиском часових обмежень у коді накопичується технічний борг та з’являються так звані «запахи коду» (Code Smells) — структурні ознаки, що сигналізують про необхідність рефакторингу.
Для виконання практичного завдання було проаналізовано вихідний код модулів розрахунку балансу клієнта, обробки повернень коштів та калькуляції вартості доставки з власного навчального вебпроєкту електронної комерції мовою PHP. У результаті аналізу було виявлено три характерні проблеми: наявність відкритих публічних полів у доменній моделі рахунку, глибоку вкладеність умовних операторів if-else у сервісі повернення коштів та численні неіменовані числові літерали у модулі тарифів доставки. Для усунення цих проблем застосовано відповідні три методи рефакторингу з каталогу Мартіна Фаулера.
3.2 Метод 1: Encapsulate Field (Інкапсуляція поля)
1. Опис проблеми та доцільність рефакторингу. Одним із головних принципів об’єктно-орієнтованого програмування є модульність та інкапсуляція — приховування внутрішніх даних об’єкта від прямого зовнішнього втручання та взаємодія з ним виключно через чітко визначений контракт методів. Коли поля класу оголошуються з модифікатором видимості public, будь-який зовнішній модуль може змінювати їхні значення напряму без відома самого об’єкта. Це призводить до порушення бізнес-інваріантів: дані відокремлюються від логіки їхньої перевірки, ускладнюється відлагодження (неможливо відстежити точку зміни поля), а зміна типу чи внутрішнього формату зберігання даних вимагає переписування всього клієнтського коду.
2. Аналіз коду до рефакторингу. У початковій версії класу рахунку клієнта CustomerAccountBad (наведено у Додатку В, підрозділ В.1) поля $ownerEmail, $balance, $bonusPoints та $isFrozen були оголошені як public. Унаслідок цього зовнішній код міг виконати операцію $account->balance -= 1200.0; навіть тоді, коли прапорець $account->isFrozen мав значення true, або встановити від’ємний баланс і від’ємну кількість бонусних балів.
3. Застосування методу рефакторингу та код після змін. Відповідно до методу Encapsulate Field (Додаток В, підрозділ В.2, клас CustomerAccountRefactored), модифікатори видимості всіх чотирьох полів було змінено з public на private. Для читання стану створено типізовані гетери getOwnerEmail(), getBalance(), getBonusPoints() та isFrozen(). Замість примітивних сетерів, які б просто перезаписували баланс, було впроваджено предметно-орієнтовані методи модифікації стану: setOwnerEmail() (перевіряє коректність формату email за допомогою filter_var), deposit() (гарантує додатну суму поповнення), withdraw() (перевіряє, чи не заморожено рахунок, чи додатна сума та чи достатньо коштів на балансі) та addBonusPoints().
4. Переваги отриманого коду. Завдяки інкапсуляції полів клас CustomerAccountRefactored повністю захищає власні інваріанти: неможливо перевести рахунок у некоректний стан або списати кошти в обхід правил безпеки. Крім того, вся логіка валідації сконцентрована в одному місці, що відповідає принципу єдиної відповідальності (SRP).
3.3 Метод 2: Replace Nested Conditional with Guard Clauses (Заміна вкладених умовних операторів захисними умовами)
1. Опис проблеми та доцільність рефакторингу. Умовні вирази зазвичай мають дві форми: перша форма — коли обидві гілки (if та else) є частиною нормальної поведінки алгоритму; друга форма — коли одна гілка є нормальною поведінкою, а інша обробляє рідкісні, граничні або помилкові ситуації. Якщо обидва види перевірок вкладати один в одного за допомогою класичних конструкцій if-else, виникає антипатерн «Стріла» (Arrow Anti-Pattern). Код зсувається вправо на 4–6 рівнів відступу, його цикломатична та когнітивна складність різко зростає, а гілки else опиняються на відстані десятків рядків від відповідних їм умов if.
2. Аналіз коду до рефакторингу. У початковому класі RefundCalculatorBad (Додаток В, підрозділ В.3) метод calculateRefund() обчислює суму повернення коштів за замовлення і містить 5 рівнів вкладених умов if-else: перевірка оплати замовлення ($isOrderPaid), перевірка скасування замовлення (!$isOrderCancelled), перевірка типу товару (!$isDigitalProduct), перевірка 14-денного терміну ($daysSincePurchase <= 14) та перевірка цілісності пакування ($isItemOpened). Через каскад вкладених блоків else наприкінці методу вкрай важко зрозуміти, яка саме умова повертає 0.0, а яка — повну суму $orderTotal.
3. Застосування методу рефакторингу та код після змін. Згідно з методом Replace Nested Conditional with Guard Clauses (Додаток В, підрозділ В.4, клас RefundCalculatorRefactored), вкладене дерево умов було інвертовано та замінено на послідовність незалежних плоских захисних умов (Guard Clauses) на початку методу. Якщо замовлення не оплачено (!$isOrderPaid) — метод негайно повертає 0.0. Якщо замовлення було скасовано до відправки ($isOrderCancelled) — метод одразу повертає повну суму $orderTotal. Якщо товар цифровий або минуло більше ніж MAX_RETURN_DAYS (14 діб) — повертається 0.0. Після проходження всіх захисних перевірок залишається простий розрахунок для основного сценарію.
4. Переваги отриманого коду. Максимальна глибина вкладеності методу зменшилася з 5 рівнів до 1 рівня, кількість блоків else скоротилася з 4 до 0, а проміжна мутабельна змінна $refundAmount стала непотрібною. Логіка методу читається зверху вниз як чіткий список бізнес-правил.
3.4 Метод 3: Replace Magic Number with Symbolic Constant (Заміна магічного числа символьною константою)
1. Опис проблеми та доцільність рефакторингу. «Магічним числом» (Magic Number) називають числовий літерал, який зустрічається безпосередньо в тексті програми без пояснення його семантичного значення. Наявність таких чисел створює дві серйозні проблеми: по-перше, інший розробник не може без зовнішньої документації зрозуміти, що саме означає число у формулі; по-друге, якщо одне й те саме граничне значення (наприклад, базова ставка ПДВ або максимальна вага посилки) використовується в кількох виразах, то при зміні бізнес-вимог висока ймовірність оновити число в одному місці й забути в іншому.
2. Аналіз коду до рефакторингу. У початковому класі ShippingCalculatorBad (Додаток В, підрозділ В.5) метод calculateDeliveryCost() містив вісім числових літералів: 2000.0 (поріг безкоштовної доставки), 120.0 (базовий тариф), 30.0 (двічі дублювався як ліміт стандартної ваги), 25.0 (доплата за кожен кілограм перевищення), 5 (двічі дублювався як кількість днів безкоштовного зберігання на складі), 40.0 (пеня за добу понаднормового зберігання), 0.015 (ставка страхування) та 1.20 (множник ПДВ). Щоб пояснити ці числа, автору початкового коду доводилося писати коментарі над кожним блоком if.
3. Застосування методу рефакторингу та код після змін. У відрефактореному класі ShippingCalculatorRefactored (Додаток В, підрозділ В.6) застосовано метод Replace Magic Number with Symbolic Constant: усі числові значення винесено у типізовані константи класу у стилі UPPER_SNAKE_CASE з вказівкою одиниць вимірювання (FREE_SHIPPING_THRESHOLD_UAH, BASE_DELIVERY_FEE_UAH, MAX_STANDARD_WEIGHT_KG, OVERWEIGHT_FEE_PER_KG_UAH, FREE_STORAGE_DAYS, STORAGE_PENALTY_PER_DAY_UAH, INSURANCE_RATE, VAT_MULTIPLIER). Також введено пояснювальні змінні $overweightKg та $extraStorageDays.
4. Переваги отриманого коду. Код став повністю самодокументованим (потреба у рядкових коментарях відпала), усунено дублювання порогових чисел 30.0 і 5 у перевірках та формулах, а зміна будь-якого тарифу тепер виконується безпечно в одному рядку оголошення константи.
3.5 Інструменти автоматизації рефакторингу та верифікація змін
У сучасній інженерній практиці розглянуті методи рефакторингу виконуються за підтримки спеціалізованих інструментів. Інтегровані середовища розробки, такі як JetBrains PhpStorm та IntelliJ IDEA, містять вбудовані автоматизовані команди: Encapsulate Fields (автоматично змінює область видимості поля на private, генерує гетери/сетери та замінює всі прямі звернення у проєкті), Invert If Condition (перетворює вкладений оператор if на захисну умову з раннім виходом) та Extract Constant (комбінація клавіш Ctrl+Alt+C виділяє числовий літерал у символьну константу класу та замінює всі його дублікати). Для пакетного автоматичного рефакторингу великих кодових баз у PHP застосовується інструмент трансформації абстрактного синтаксичного дерева Rector.
Обов’язковою умовою безпечного рефакторингу є верифікація незмінності зовнішньої поведінки системи за допомогою автоматизованих тестів PHPUnit. Для всіх трьох розглянутих модулів було виконано порівняльне тестування початкових і відрефакторених класів на однакових наборах вхідних даних, яке підтвердило повну еквівалентність розрахунків при суттєвому покращенні внутрішньої структури коду.

4 ВИСНОВКИ
У результаті виконання практичного завдання № 2 було досліджено та практично застосовано методи рефакторингу програмного коду з каталогу Мартіна Фаулера на прикладах власного програмного проєкту. Основні підсумки виконаної роботи:
– Було розглянуто теоретичні основи процесу рефакторингу, поняття технічного боргу та «запахів коду» (Code Smells), а також критерії збереження зовнішньої функціональної поведінки системи під час трансформації коду.
– Практично застосовано метод Encapsulate Field (Інкапсуляція поля) до класу рахунку клієнта CustomerAccount, що дозволило закрити прямий доступ до полів балансу й статусу блокування та забезпечити централізовану перевірку бізнес-інваріантів у методах deposit() і withdraw().
– Застосовано метод Replace Nested Conditional with Guard Clauses (Заміна вкладених умовних операторів захисними умовами) у сервісі RefundCalculator, завдяки чому глибину вкладеності умов зменшено з 5 до 1 рівня та повністю усунено каскад гілок else.
– Використано метод Replace Magic Number with Symbolic Constant (Заміна магічного числа символьною константою) у класі ShippingCalculator, що дозволило замінити 8 неочевидних числових літералів на типізовані самодокументовані константи та усунути дублювання граничних значень.
– Отримано практичні навички поєднання покрокового рефакторингу з інструментами IDE (PhpStorm), засобами автоматичної модернізації коду (Rector), статичними аналізаторами (PHPStan, SonarQube) та модульним тестуванням (PHPUnit).

14  final class CustomerAccountRefactored
15  {

17      private float $balance;
18      private int $bonusPoints = 0;
19      private bool $isFrozen = false;
20

22      {
23          $this->setOwnerEmail($ownerEmail);
24          if ($initialBalance < 0.0) {

46      }
47  
48      public function getBonusPoints(): int
49      {

51      }
52  
53      public function isFrozen(): bool
54      {
55          return $this->isFrozen;
56      }
57

59      {
60          $this->isFrozen = true;
61      }
62

64      {
65          if ($amount <= 0.0) {
66              throw new InvalidArgumentException('Сума поповнення повинна бути більшою за нуль.');
67          }
68          $this->balance = round($this->balance + $amount, 2);
69      }
70  
71      public function withdraw(float $amount): void
72      {
73          if ($this->isFrozen) {
74              throw new DomainException('Операції заблоковано: рахунок заморожено.');

77              throw new InvalidArgumentException('Сума списання повинна бути більшою за нуль.');
78          }
79          if ($amount > $this->balance) {
80              throw new DomainException('Недостатньо коштів на рахунку для списання.');
81          }
82          $this->balance = round($this->balance - $amount, 2);
83      }

 7  /**

 9   * Replace Magic Number with Symbolic Constant.

11   */
12  final class ShippingCalculatorRefactored
13  {
14      public const float FREE_SHIPPING_THRESHOLD_UAH = 2000.0;
15      public const float BASE_DELIVERY_FEE_UAH = 120.0;
16  
17      public const float MAX_STANDARD_WEIGHT_KG = 30.0;
18      public const float OVERWEIGHT_FEE_PER_KG_UAH = 25.0;
19  
20      public const int FREE_STORAGE_DAYS = 5;
21      public const float STORAGE_PENALTY_PER_DAY_UAH = 40.0;
22  
23      public const float INSURANCE_RATE = 0.015;
24      public const float VAT_MULTIPLIER = 1.20;
25  
26      public function calculateDeliveryCost(
27          float $orderSubtotal,
28          float $weightKg,
29          int $storageDays,
30      ): float {
31          $deliveryCost = 0.0;
32  
33          if ($orderSubtotal < self::FREE_SHIPPING_THRESHOLD_UAH) {
34              $deliveryCost += self::BASE_DELIVERY_FEE_UAH;
35          }
36  
37          if ($weightKg > self::MAX_STANDARD_WEIGHT_KG) {
38              $overweightKg = $weightKg - self::MAX_STANDARD_WEIGHT_KG;
39              $deliveryCost += $overweightKg * self::OVERWEIGHT_FEE_PER_KG_UAH;
40          }
41  
42          if ($storageDays > self::FREE_STORAGE_DAYS) {
43              $extraStorageDays = $storageDays - self::FREE_STORAGE_DAYS;
44              $deliveryCost += $extraStorageDays * self::STORAGE_PENALTY_PER_DAY_UAH;
45          }
46  
47          $insuranceFee = $orderSubtotal * self::INSURANCE_RATE;
48  
49          return round(($deliveryCost + $insuranceFee) * self::VAT_MULTIPLIER, 2);
50      }
51  }
